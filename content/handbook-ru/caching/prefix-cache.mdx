## Проблема

Cache может быть включён, но `cached_tokens` остаётся низким. Часто проблема не в provider, а в request shape.

## Симптомы

- Timestamps, request IDs или tenant fields появляются в начале.
- Tool lists меняют порядок или содержимое между turns.
- Agent loops используют более короткие dynamic prompts, которые становятся дороже после cache misses.
- Round-robin routing размазывает warm prefixes по replicas.

## Ментальная модель

Prefix cache требует три вещи: начало должно совпадать, request должен попасть туда, где prefix warm, и cache должен жить достаточно долго для reuse.

## Архитектура

Стабилизируй system prompt, tool schemas и response formats. Перенеси dynamic fields поздно или в metadata. Используй canonical serialization. По возможности сохраняй append-only conversation growth. Route repeated prefixes через affinity или prefix-aware routing.

## Метрики

Отслеживай cached tokens, cache read input tokens, prefix hash, tools count, schema version, TTFT, route, replica, prompt version, warmup count и cache eviction indicators.

## Компромиссы

Большой стабильный tool list может быть дешевле маленького dynamic list в agent loop. Но большие tool lists могут ухудшать model tool-choice quality, особенно на smaller models.

## Анти-паттерны

- Current time в первых system tokens.
- Плавающий `tools` order из unordered registry.
- Dynamic `requestId` внутри JSON schema.
- Переписывание начала history вместо append-only growth.
- Parallel fan-out до прогрева shared prefix.
- Plain round-robin для длинных shared prefixes.

## Пример

В multi-turn agent изменение tool subset на каждом step может снизить raw prompt length, но сбросить cacheable prefix. Stable tool declaration с route-level allowed tools или constrained decoding может сохранить reuse.

## Шаблон решения

Для cache change запиши before/after prompt shape, prefix hash stability, cached token distribution, TTFT, cost per task и quality impact.
