Два запроса могут решать одну и ту же задачу и почти целиком совпадать. Но если в начало попала текущая дата или поменялся порядок описаний инструментов, общий префикс обрывается раньше, чем мы рассчитывали.

`audit-prompt-caching` помогает найти такое место. Скилл разбирает код сборки запроса, инструкции, инструменты, историю диалога и настройки маршрутизации. Локальные Python-скрипты сравнивают готовые запросы и разбирают сохранённые данные об использовании кэша.

Начать можно с кода проекта. Если для вывода нужны логи или метрики, скилл подскажет, какие именно собрать.

## Как попробовать

Установите скилл:

```bash
npx skills add https://github.com/sernote/audit-prompt-caching --skill audit-prompt-caching
```

Откройте новую сессию Codex в своём проекте и дайте ему задачу:

```text
Проверь этот проект с $audit-prompt-caching.
Начни с кода, который собирает и отправляет LLM-запросы.
Найди, где меняется общий префикс, и объясни, что стоит исправить.
Укажи, по каким данным проверить результат.
```

Скилл ищет меняющиеся поля в начале промпта, перестановки инструментов и схем, изменения истории между шагами. Затем проверяет настройки провайдера и роутера: одинаковые запросы могут попадать на разные реплики, каждая со своим кэшем.

Код и остальные способы установки лежат [на GitHub](https://github.com/sernote/audit-prompt-caching).

## Пример: дата перед инструкциями

В репозитории есть два запроса на разбор обращения в поддержку. Инструкции у них одинаковые, а время, номер обращения и сообщение клиента различаются. В исходном варианте эти меняющиеся поля стоят первыми. Переносим их после инструкций:

```text
До:    дата, номер обращения, сообщение → инструкции
После: инструкции → дата, номер обращения, сообщение
```

Содержание запросов осталось прежним. В этом примере их общее начало выросло с 43 до 254 байт.

Чтобы повторить сравнение, нужны Git и Python 3.10 или новее:

```bash
git clone --depth 1 https://github.com/sernote/audit-prompt-caching.git
cd audit-prompt-caching
python3 audit-prompt-caching/scripts/prefix_stability_check.py --json \
  examples/first-audit/before-a.txt examples/first-audit/before-b.txt
python3 audit-prompt-caching/scripts/prefix_stability_check.py --json \
  examples/first-audit/after-a.txt examples/first-audit/after-b.txt
```

В выводе смотрите на `stable_prefix_bytes`:

```text
До:    43
После: 254
```

Обе команды возвращают код `1`: полные запросы всё ещё различаются, так и задумано. Числа показывают длину общего начала файлов в байтах UTF-8. Чтобы узнать, сработал ли кэш, нужны данные самого вызова.

[Полные запросы и вывод скрипта](https://github.com/sernote/audit-prompt-caching/blob/main/examples/first-audit/README.md) можно посмотреть отдельно. Для своей задачи [запустите скилл в проекте](#your-project) или сравните скриптом два готовых запроса одного сценария. Время и пользовательский ввод должны различаться так же, как в обычной работе приложения.

## Как проверить результат

После изменения промпта повторите вызовы и посмотрите, сколько входных токенов провайдер прочитал из кэша. Если API отдельно показывает создание кэша, проверьте и чтение в следующих вызовах. Названия полей и условия зависят от API; в репозитории есть справки для [OpenAI](https://github.com/sernote/audit-prompt-caching/blob/main/audit-prompt-caching/references/openai.md), [Anthropic](https://github.com/sernote/audit-prompt-caching/blob/main/audit-prompt-caching/references/anthropic.md) и [Bedrock](https://github.com/sernote/audit-prompt-caching/blob/main/audit-prompt-caching/references/bedrock.md).

Затем сравните время до первого токена и стоимость вызовов на той же нагрузке. Это отвечает на главный вопрос: помогло ли изменение приложению. Бывает, что кэш читается, а ответ всё равно задерживается в очереди. Такой случай разбираю в статье [«Тёплый кэш — ещё не быстрый ответ»](/blog/cache-locality-is-a-routing-problem).

## Если проблема в маршрутизации

Проверьте, куда попал повторный запрос, что роутер знал о кэше выбранной реплики и сколько времени запрос провёл в очереди.

Скрипт `analyze_routing_logs.py` связывает решение роутера и результат попытки по `run_id`, `request_id` и `attempt_id`. Для него нужно подготовить JSONL в [описанном формате](https://github.com/sernote/audit-prompt-caching/blob/main/audit-prompt-caching/references/routing-evidence.md). Там же есть примеры входных данных; произвольный лог роутера сначала придётся привести к этому формату.

### Почему HTTP 200 недостаточно

В отдельном эксперименте vllm-router отправляет три запроса тестовому серверу. Два ответа приходят целиком, а в третьем сервер намеренно пропускает завершающие события. При этом у всех трёх HTTP 200, а счётчик circuit breaker у роутера отмечает три успешных обращения. Поэтому завершение ответа нужно проверять на стороне клиента.

[Устройство стенда](https://github.com/sernote/audit-prompt-caching/blob/b53cd3f3fc69f044952d99cd6046f274a80f1ee2/examples/router-observation/README.md) и [сохранённые события](https://github.com/sernote/audit-prompt-caching/blob/b53cd3f3fc69f044952d99cd6046f274a80f1ee2/examples/router-observation/recorded/2026-09-05/README.md) доступны в репозитории. Сервер имитирует ответы без модели и KV-кэша: этот эксперимент показывает поведение HTTP-потока. Подробнее о том, какие данные доступны роутеру, пишу в статье [«Что кэш-роутер знает о кэше»](/blog/what-cache-router-knows).
