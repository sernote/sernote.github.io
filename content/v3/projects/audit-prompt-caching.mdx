`audit-prompt-caching` помогает искать вероятные причины, по которым повторяющиеся LLM-запросы не получают ожидаемого повторного использования кэша, и собирать доказательства для проверки гипотез. Проблема часто прячется за общим симптомом: выросла стоимость, удлинился time to first token, cached-token поле остаётся нулевым или одинаковая агентная сессия ведёт себя по-разному на соседних шагах.

Репозиторий содержит переносимый Codex skill и небольшие Python-скрипты на стандартной библиотеке. Они проверяют артефакты проекта: построители промптов, сериализованные payloads, tool schemas, usage logs и конфигурацию маршрутизации. Проект дополняет runtime observability и gateway, но не заменяет их.

## Для кого

Инструмент рассчитан на инженера, у которого уже есть материалы для проверки. Это может быть код сборки запроса, два готовых JSON-файла, экспорт данных об использовании, фрагмент данных для расчётов или конфигурация развёртывания. Если известно только то, что «кэш не работает», skill сначала помогает составить план сбора доказательств.

AI- и backend-инженеры используют аудит, когда system prompt или tools незаметно меняются. Разработчикам агентов полезны проверки порядка инструментов, compaction и стабильности ранней истории. Platform/SRE-командам ближе маршрут, replica locality, KV pressure и различия provider telemetry.

## Что проверяет аудит

Основная поверхность начинается в исходниках. Skill ищет динамические timestamp и request identifiers в раннем префиксе, недетерминированную сериализацию tools, изменение schema между шагами, перестановку system и user blocks, truncation и compaction. Для provider API он отделяет документированную семантику cache read/write от предположений приложения.

Вторая поверхность — маршрут запроса. Стабильный payload способен попадать на разные provider paths или self-hosted replicas. Тогда форма запроса совпадает, а локальность кэша теряется. Это требует route evidence, а не очередного переписывания промпта.

Третья поверхность — измерение. Скрипты читают явные cache fields, токены и latency только из переданных файлов. Provider usage и billing export остаются авторитетными. Локальный расчёт ROI работает с заданными допущениями; bundled fixture показывает формат, но не обещает production-экономию.

Аудит строится как цепочка доказательств. Сначала инженер находит место, где приложение собирает запрос. Затем сохраняет rendered payloads для двух повторов, сопоставляет их с route и usage, формулирует наиболее ранний drift и только после этого предлагает изменение. Такой порядок удерживает расследование от популярной ошибки: сразу переставить блоки промпта, не выяснив, теряется ли reuse из-за layout, маршрута, eviction или неподходящего workload.

## Быстрый старт

Установите публичный skill командой из [README](https://github.com/sernote/audit-prompt-caching#quick-start):

```bash
npx skills add https://github.com/sernote/audit-prompt-caching --skill audit-prompt-caching
```

После установки начните новую сессию Codex, чтобы skill появился в доступном наборе. Затем вызовите его явно:

```text
Use $audit-prompt-caching to audit this repo for prompt-cache misses,
unstable prompt prefixes, dynamic tools/schemas, routing issues,
and deployment cache-locality problems.
```

Для точечной локальной проверки клонируйте release и запустите один из stdlib-скриптов. Например, layout linter принимает Chat-style `messages` и Responses-style `input` payloads:

```bash
python3 audit-prompt-caching/scripts/layout_linter.py \
  fixtures/layout/good_openai_request.json
```

Команда возвращает JSON. Нулевой exit code означает, что реализованные правила не нашли нарушения; это не сертификат cache hit. Ненулевой код при findings пригоден для CI или source-controlled evidence, если команда заранее согласовала ожидаемые правила.

## Локальность и границы данных

Проект не захватывает live traffic и не подключается к провайдеру сам. Пользователь экспортирует входные данные отдельно. Перед аудитом нужно удалить customer content, credentials, идентификаторы и закрытые URL либо заменить их эквивалентной синтетикой.

Готовые fixtures в репозитории синтетические и предназначены для демонстрации формы. Для реального расследования подготовьте репрезентативные записи, очищенные от чувствительных данных: собранные запросы, данные провайдера об использовании, хеши префиксов, метки маршрута или конфигурацию развёртывания. Храните их по правилам своей организации. Публичный репозиторий не становится допустимым местом для журналов рабочей системы только потому, что скрипт работает локально.

Скрипты не отправляют содержимое во внешний сервис, но установка skill и получение репозитория требуют обычного сетевого доступа к источнику. Если аудит запускает агент, границу данных определяют его runtime, разрешения инструментов и подключённые сервисы. Перед использованием в закрытой среде проверьте закреплённую версию и код по внутреннему процессу.

## Ограничения

Статический аудит видит форму и известные анти-паттерны. Он не доказывает, что провайдер записал кэш, что запрос попал на нужную replica или что KV blocks не были вытеснены. Эти выводы подтверждаются runtime telemetry, provider response fields, traces и billing export.

Правила зависят от API и версии. Исправление, полезное для одного провайдера, способно быть бессмысленным для другого. Перед изменением layout сверяйте текущую официальную документацию и проверяйте результат на повторяемой выборке.

Fixture ROI в README — демонстрационный расчёт, а не production guarantee. Проект распространяется по [лицензии MIT](https://github.com/sernote/audit-prompt-caching/blob/v0.1.3/LICENSE) и предоставляется без заявленного support SLA. Вопросы эксплуатации, обновления и интерпретации результатов остаются у пользователя.
